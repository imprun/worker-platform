# Worker Platform 요구사항

팀이 자체 Kubernetes 클러스터의 ATE Actor에서 공통 런타임으로 워커 앱 패키지를 실행하고, Gateway API로 호출하며, 장시간 작업을 실행 ID로 추적할 수 있어야 한다. 앱 개발자는 처리 로직을 OCI 패키지로 게시하고 패키지 digest를 수정해 배포한다. 첫 인수 대상은 일반 HTTP 책 스크래퍼와 사이트 계정 로그인 상태를 사용하는 브라우저 스크래퍼다. 웹훅이나 데이터 처리 워커도 같은 실행 계약을 사용할 수 있다.

첫 운영 릴리스는 워커 앱 하나에 제출하는 **단일 Job**을 지원한다. 장애 재시도, 사용자 개입(HITL)을 통한 재인증, 취소와 결과 조회는 같은 실행의 수명주기에 속한다. 여러 Job을 연결하는 워크플로와 A2A 연동은 후속 범위다. `windforce-core`는 Windmill을 참고해 ATE 없이 만든 워커 POC이며, 그 경험을 실행 기록과 풀별 운용 요구사항에 반영했다. [Windmill의 Job 모델](https://www.windmill.dev/docs/core_concepts/jobs)

현재의 ATE 동기 배포와 첫 운영 릴리스의 구성을 [아키텍처](architecture.md)에서 확인할 수 있다. 아래는 첫 운영 릴리스의 인수 기준이다. [Job 상세 설계](job-execution-design.md) · [검토 근거와 출시 기준](design-review.md)

## 기능과 인수 기준

| ID | 요구사항 | 인수 기준 |
| --- | --- | --- |
| R1 | **ATE 직접 설치와 Gateway 호출.** 운영자가 문서화된 Kubernetes·GatewayClass·ATE 조합으로 별도 ARM64 gVisor 풀에 설치한다. | ATE Control API로 Echo Actor를 준비하고 Gateway에서 Router로 mTLS를 연결해 응답을 받는다. CRD 검증과 실제 Gateway–Router mTLS 왕복을 각각 확인한다. 응답이 구분되는 두 시험 Actor로 대상 헤더 덮어쓰기를 입증한다. 허용한 egress만 성공한다. |
| R2 | **앱 패키지 배포와 롤백.** 워커는 앱 패키지 digest와 승인된 런타임 프로필을 선언한다. | 동일 런타임 이미지로 앱 패키지 digest만 바꾼다. v2 패키지 로드와 초기화가 완료될 때까지 같은 URL은 v1을 응답한다. 패키지 검증·로드 실패 시 v1 응답이 지속되고, 롤백 시 보존된 v1 서비스 Actor를 재사용한다. 같은 두 digest와 설정을 다시 적용하면 같은 리비전을 얻는다. |
| R3 | **Job 접수와 결과 조회.** 접수한 리비전·입력을 영속화한 뒤 `202`와 실행 ID를 반환한다. | 접수 서비스 재시작 뒤에도 ID로 조회된다. 같은 범위의 멱등 키·입력을 동시에 보내면 같은 ID, 같은 키로 다른 입력을 보내면 `409`다. 전체 접수 한도가 찬 경우에도 기존 키의 재요청은 같은 ID를 받는다. |
| R4 | **실행 장애 복구와 정리.** 시도는 접수 당시 리비전의 런타임 이미지와 앱 패키지로 실행한다. 결과와 점유 슬롯은 실행 ID로 추적 가능하다. | v1으로 접수한 80초 Job 도중 앱 패키지 v2를 게시하고 실제 배정된 테스트 Worker를 종료하면 다른 Worker에서 접수 당시 런타임과 v1 패키지를 사용한다. 원래 ID의 결과는 한 건이며 Run의 점유 슬롯은 0개다. 늦은 완료 보고는 결과를 바꾸지 못한다. 생성·시작·완료 응답 유실과 컨트롤러 재시작 후에도 중복 실행권과 슬롯 누수가 없다. |
| R5 | **풀별 용량과 과부하 제어.** 일반 HTTP와 브라우저 풀의 자원 및 접수·슬롯 한도를 운영자가 적용한다. | 서비스 복제본 둘 이상에서 브라우저 풀을 포화시켜도 해당 풀의 한도가 유지되고 HTTP 풀 작업이 완료된다. 신규 접수 여유가 없으면 `429`를 반환한다. 플랫폼 예약과 ATE 실제 배정으로 각각 확인한다. |
| R6 | **환경과 앱 권한.** 개발계에서 검증한 런타임 이미지와 앱 패키지의 digest를 운영계로 승격하고 실행 설정과 시크릿은 환경별로 해석한다. | 같은 실행 ID로 다른 앱이나 환경에서 상태·결과를 조회할 수 없다. 두 앱은 같은 멱등 키를 독립적으로 쓸 수 있다. 승인되지 않은 계정이나 프로필을 사용한 요청은 거부한다. |
| R7 | **사이트 로그인 상태 재사용과 HITL 재개.** 새 Actor는 승인된 계정의 로그인 상태와 앱 체크포인트를 이어서 쓴다. | 모의 사이트에서 Actor를 교체해도 재로그인 없이 보호된 페이지를 조회한다. 만료 뒤 동일 Run이 슬롯 0개로 사용자를 기다린다. 동일 인증 완료를 동시에 두 번 보내도 고정 리비전에서 한 번만 재개되고 결과가 한 건이다. 두 Run의 동시 만료에도 계정 갱신은 한 번에 하나다. |
| R8 | **조회와 운영.** 운영자는 실행 목록·검색, 실행 상세 타임라인과 풀 현황을 본다. | 운영자가 리비전·시도·Worker·실패 사유·슬롯 반환·로그를 실행 ID로 추적한다. ATE 관측 실패와 정상 0건이 구분된다. 상태·결과·운영 조회로 Actor를 깨우지 않으며, 같은 Run의 중복 취소는 상태 변경을 한 건만 기록한다. |

## 실행 결과와 재인증의 보장

- 플랫폼은 승인된 현재 시도의 결과를 **한 실행에 한 건** 공개한다. 장애 재시도 때문에 앱 코드가 다시 실행될 수 있다. 외부 사이트에 쓰는 앱은 실행 ID와 단계 식별자를 외부 멱등 키로 사용하거나 재시도 전에 처리를 대조한다.
- 사이트 로그인 상태는 Worker Platform 내부 계정 세션 모듈이 테넌트·환경·사이트·계정 범위로 암호화해 관리한다. Actor에는 허용된 실행 수명 동안 그 실행의 계정만 제공한다. 로그와 실행 이력에는 세션 참조와 버전만 남긴다.
- 사용자의 응답을 기다리는 Run의 Actor 슬롯은 0개다. 인증에 브라우저가 필요한 경우 사용자가 인증을 시작한 뒤 실제 인증을 수행하는 동안만 별도 슬롯을 배정한다. 인증을 완료하면 같은 실행 ID, 접수 당시 리비전과 앱이 저장한 지점으로 돌아간다. 새 Actor가 인증 상태를 사용할 수 있는지는 사이트 정책에 따르며, R7은 재현 가능한 모의 사이트로 입증한다. [브라우저 인증 상태 재사용](https://playwright.dev/docs/auth)

## 개발 순서

1. **ATE 직접 배포와 공통 런타임의 앱 로드**를 구현한다. R1에서 GatewayClass와 ATE 정책을 검증하고, R2에서 앱 패키지 단독 갱신과 롤백을 검증한다.
2. **영속 Job 실행**의 최소 경로를 만들고 슬롯, 권한, 취소를 Run 상태 전이와 함께 구현한다. R3·R4의 응답 유실과 장애 시험을 자동화한다.
3. **여러 풀·환경과 운영 조회**를 연결한다. R5·R6·R8을 다중 복제본에서 확인하고, 실행 상세에 DB 기록과 ATE 관측값을 연결한다.
4. **계정 세션과 HITL**을 모의 사이트와 운영 화면에서 검증한다. R7에서 Job의 접수·결과·슬롯 계약을 같은 흐름으로 확인한다.

출시 검증은 격리된 개발계에서만 수행한다. 준비 Actor의 전환, 장애 주입 대상, Run 결과, 반환된 슬롯을 증거로 남긴다. [시험 증거와 확인 상태](design-review.md)
